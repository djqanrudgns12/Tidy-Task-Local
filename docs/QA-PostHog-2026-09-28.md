# PostHog 연동 점검 — 2026-09-28

## 결론

5.6.x 통계 누락은 실제로 확인되었습니다. 배포된 5.6.0과 5.6.2 설치 파일에는 PostHog 공개 수집 토큰이 없었습니다. 기존 구현은 토큰이 없으면 오류 없이 수집을 끄므로, 자동 참여 코드가 있어도 이벤트가 만들어지거나 전송되지 않습니다.

이전 동의 여부는 현재 수집 조건이 아닙니다. 정상 수집 설정을 포함한 배포 빌드는 예전 `consent:false` 파일도 읽어 자동 참여를 시작합니다. 관련 Rust 회귀 테스트를 이번 점검에서 실행해 통과했습니다. 사용자에게 다시 동의를 묻는 팝업이나 참여 버튼은 없습니다.

운영 프로젝트의 공개 토큰과 US 수집 주소를 로컬 빌드 설정에 복구하고, 잘못된 설정으로 다시 배포하는 것을 막는 검증을 추가했습니다. 기존 배포 파일은 그대로 보존했습니다. 설치된 구버전이 이 변경을 받으려면 수정 내용을 포함한 새 패치 버전의 설치 파일을 빌드하고 배포해야 합니다. 이 점검에서는 GitHub 게시, 버전 변경, 커밋 및 푸시를 하지 않았습니다.

일반 버전별 조회:

```sql
SELECT properties.app_version AS version,
       properties.environment AS environment,
       count() AS events,
```

## 설치 파일과 빌드 설정 증거

점검 시작 시 `src-tauri/.env`에는 PostHog 토큰·호스트·개발 허용 설정이 없었고, 셸 환경변수에도 설정이 없었습니다. release 빌드 스크립트의 저장된 출력에서도 `POSTHOG_PROJECT_TOKEN`이 빈 값이었습니다. 호스트만 기본값 `https://us.i.posthog.com`으로 들어갔습니다.

GitHub API의 게시된 첨부 파일 SHA-256과 로컬 설치 파일 SHA-256을 비교해 두 파일이 일치함을 확인했습니다. 공식 7-Zip 도구를 QA 폴더에 압축 해제해 사용했으며, Tidy Task 설치 파일은 설치하거나 실행하지 않고 내부 `tidy_task.exe`만 추출했습니다.

## 기존 미동의자와 업데이트 후 자동 참여

`src-tauri/src/analytics.rs`의 `Disk` 구조체에는 현재 `consent` 필드가 없습니다. 구버전 JSON의 해당 필드는 무시됩니다. `enabled()`는 토큰 설정 유무만 확인합니다.

실행 순서는 다음과 같습니다.

1. 통계 저장 파일을 읽습니다. 예전 `consent:false`가 남아 있어도 수집 여부에 쓰지 않습니다.
2. 운영 수집 토큰·허용 호스트를 확인합니다. debug 빌드는 추가로 `POSTHOG_DEV_ENABLED=1`이 필요합니다.
3. 유효한 수집 설정이면 앱 시작 이벤트를 만듭니다. 설치 ID가 없으면 임의의 새 ID를 만듭니다.
4. 실제 창 조작이 발생하면 세션·활성 설치 이벤트를 만듭니다.
5. 일반적으로 15초 간격으로 PostHog batch API에 보냅니다.

`old_opt_out_file_migrates_to_automatic_collection` 테스트는 예전 `consent:false` 파일에서 설치 ID와 `installation_first_seen`, `active_minute`가 생성되는 것을 검증하며 이번 실행에서 통과했습니다. 5.6.0 소스 태그에도 이 자동 참여 로직이 있습니다.

따라서 기존 미동의자가 자동 참여하지 않는 원인은 동의 값이 아니라 이번 배포 파일의 토큰 누락입니다. 정상 설정을 포함한 새 배포본으로 업데이트하면 자동 수집을 시작합니다. 이전에 수집되지 않은 5.6.x 사용 기록은 생성된 이벤트 자체가 없어 소급 복원할 수 없습니다.

- 해당 시리즈에는 `environment = production` 필터가 있고, 내부·시험 사용자 제외가 켜져 있습니다. 이 지표에 앱 버전 제한은 없었습니다.
- 프로젝트 시간대는 `Asia/Seoul (UTC+9:00)`입니다.
- 제외 코호트 `Internal / Test users`는 현재 0명입니다. 이번 누락을 설명하는 제외 대상은 없었습니다.
- 앱 실행은 `app_started`로 기록하지만, 그냥 켜두는 것만으로는 `active_minute`가 생기지 않습니다. 화면이 보이는 상태의 실제 클릭·키 입력·입력·스크롤이 필요합니다. 프로그램에서 만든 가짜 DOM 이벤트는 무시합니다.
- 같은 설치에서 여러 창을 사용해도 ID를 공유하므로 일별 활성 설치는 1로 셉니다. 계정이 없으므로 실제 사람 수보다는 설치 단위입니다. 다른 PC 또는 앱 데이터 초기화 후의 새 ID는 별도 설치로 관측될 수 있습니다.
- `active_minute` 이벤트 총합은 실제 조작이 관측된 분의 수이며, 창을 켜둔 총 시간이나 정확한 사용 시간은 아닙니다.
- 학급 툴킷 창은 현재 `window_kind = other`로 합쳐집니다. 투표·주사위·타이머별 자세한 사용량은 별도의 이벤트가 없으므로 구분되지 않습니다. 이 제한은 전체 활성 설치 누락과는 별개입니다.
- 프로필 생성을 끈 이벤트를 보내므로 Persons 목록 개수로 이용자 수를 판단하면 안 됩니다. PostHog의 personless 처리도 이벤트 집계를 지원합니다. [PostHog 공식 처리 설명](https://github.com/PostHog/posthog/blob/master/docs/published/handbook/engineering/person-processing.md).

## 전송되는 정보와 전송 조건

전송 항목은 임의 설치 ID, 이벤트 UUID·발생 시각, 앱 버전, 운영체제·아키텍처, 환경, 제한된 기능 종류·횟수·오류 코드 등입니다. 메모·할 일 본문, 학생 이름, 학교 정보, 파일 경로, 실제 입력 내용, 오류 원문, 화면 녹화는 보내지 않습니다. Rust 허용 목록 밖의 기능 이벤트도 거부합니다.

`$process_person_profile=false`, `$geoip_disable=true`, `$ip=0.0.0.0`을 지정합니다. 수신 서버에는 네트워크 연결 IP가 보일 수 있어 완전한 익명성을 보장한다는 뜻은 아닙니다.

전송 실패 이벤트는 로컬 대기열에 보관하고 재시도합니다. 일반 전송은 15초 간격, 실패 시 간격은 최대 15분까지 늘어납니다. 최대 대기열은 1,000건, 보관 기간은 7일입니다. 저장소에 ID를 보존할 수 없으면 이용자를 매번 새로 세는 것을 막기 위해 해당 실행의 수집을 끕니다. 인터넷·학교망 연결 실패나 저장소 문제가 있는 모든 설치의 수신을 보장할 수는 없습니다.

수정 내용을 포함한 새 패치 버전으로 정상 `npm run release`를 수행하고, 설치 파일과 `latest.json`을 게시해야 기존 5.6.x 사용자에게 변경이 전달됩니다. 같은 버전의 `.env` 수정이나 같은 설치 파일의 재게시로는 자동 업데이트가 적용되지 않습니다.
