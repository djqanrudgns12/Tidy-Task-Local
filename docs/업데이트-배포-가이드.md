# 업데이트 배포 가이드

Tidy Task는 **GitHub Releases**를 "공식 배포처"로 삼습니다. 새 버전이 올라오면 앱이 스스로 알아채고,
사용자가 **[지금 업데이트]** 한 번만 누르면 앱이 직접 내려받아 설치합니다. 별도의 서버나 비용은 필요 없습니다.

---

## 1. 이 시스템은 어떻게 동작하나요?

```
[개발자] npm run release → GitHub 릴리스에 설치 파일 + latest.json 첨부
              ↓
[앱] 시작 2초 뒤, 이후 30분마다 GitHub에 "최신 버전이 뭐예요?" 문의 (매니저 창 1개만)
              ↓
[사용자] 창 위에 얇은 띠: "🎉 새 버전 v5.5.3 이 나왔어요" → 안내 창 → [지금 업데이트]
              ↓
[앱] latest.json 확인 → 설치 파일 내려받기(진행률) → 서명 확인
              ↓
[앱] 알림장·명단 창과 모든 메모 창에 "저장하고 입력을 잠가 주세요" → 창마다 "끝났다"는 답을 받음
              ↓
[앱] 업데이트 직전 사본(tidy-task-config.before-update.json) → 설치 프로그램 실행 → 앱 종료
              ↓
[설치 프로그램] 진행률만 보여 주며 자동 설치 → 새 버전을 다시 엽니다
```

**핵심 설계**

| 항목 | 내용 | 이유 |
|---|---|---|
| 확인 주체 | **매니저 창 1개만** | 창을 10개 켜도 GitHub 호출은 1회. 알림도 1번만 뜹니다 |
| 확인 주기 | 부팅 2초 뒤 강제 확인 + 이후 30분마다 | 새 릴리스를 빠르게 알리면서 GitHub 무료 한도(시간당 60회)를 지킵니다 |
| 설치 방식 | 앱이 직접 내려받아 설치 (`src-tauri/src/app_update.rs`) | 앱이 받은 파일에는 "인터넷에서 받은 파일" 표시가 없어 **"Windows의 PC 보호" 경고가 뜨지 않습니다** |
| 파일 확인 | 우리 서명 키로 서명한 파일만 설치 | 중간에 바뀌거나 다른 사람이 만든 파일은 절대 설치하지 않습니다 |
| 데이터 보호 | 모든 창이 저장을 마쳤다고 **답해야만** 설치 | 설치 단계에서 앱이 곧바로 끝나므로, 기다리기만 해서는 저장 완료를 보장할 수 없습니다 |
| 실패 시 | 이유를 알려 주고 **직접 내려받기**(예전 방식) 버튼을 보여 줌 | 학교 보안 프로그램 등으로 자동 설치가 막혀도 업데이트할 길을 남깁니다 |
| 사용자 선택 | "나중에"(하루) / "이 버전 건너뛰기" | 선택은 디스크에 저장되어 앱을 꺼도 유지됩니다 |

> **처음 한 번은 직접 설치해야 합니다.** 앱 안 설치 기능은 5.5.2 다음에 배포하는 버전부터 들어 있습니다.
> 5.5.2 이하 사용자는 그 버전 한 번만 예전처럼 안내 창의 링크로 내려받아 설치합니다(PC 보호 경고도 그때가 마지막).
> 그 뒤로는 앱 안에서 설치됩니다. (아래 예시의 5.5.3은 그 첫 버전을 가정한 번호입니다)

## 2. 업데이트 서명 키 (가장 중요)

앱은 **우리 서명 키로 서명한 설치 파일만** 설치합니다. 앱 안에는 짝이 되는 공개 키가
`src-tauri/tauri.conf.json`의 `plugins.updater.pubkey`로 들어 있습니다.

| 파일 | 위치 | 성격 |
|---|---|---|
| 개인 키 | `C:\Users\User\.tauri\tidy-task-updater.key` | **비밀.** Git에 올리지 않습니다 |
| 공개 키 | 같은 폴더의 `.key.pub` (= tauri.conf.json의 pubkey) | 공개해도 됩니다 |

- ⚠️ **개인 키를 잃어버리면** 이미 설치된 앱들에 더는 자동 업데이트를 보낼 수 없습니다.
  모든 사용자가 새 버전을 직접 내려받아 다시 설치해야 합니다. **USB나 개인 클라우드에 따로 백업해 두세요.**
- ⚠️ **새 키를 만들지 마세요.** 새 키로 서명한 파일은 기존 앱이 모두 거부합니다.
  컴퓨터를 바꿨다면 백업해 둔 키를 같은 위치에 복사하면 됩니다.
- 키에는 암호를 걸지 않았습니다. 암호가 있는 키로 바꾸려면 `src-tauri/.env`에
  `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`를 적습니다. 키를 다른 곳에 두려면 `TAURI_SIGNING_PRIVATE_KEY_PATH`를 적습니다.
- 이 서명은 Windows의 코드 서명 인증서와 다른 것입니다. 무료이며, "알 수 없는 게시자" 표시와는 관계가 없습니다.

## 3. 새 버전을 배포하는 방법 (개발자가 할 일)

### ① 버전 번호 올리기 — 기준은 `package.json`

```jsonc
// package.json
"version": "5.5.3"   // ← 여기부터 고칩니다
```

> **설치 버전의 기준:** `src-tauri/tauri.conf.json`이 `"version": "../package.json"`으로
> package.json을 바라보도록 연결해 두었습니다. 설치 파일과 앱 업데이트 비교는 이 버전을 사용합니다.
>
> `package-lock.json`, `src-tauri/Cargo.toml`과 `Cargo.lock`의 앱 패키지 버전,
> 도움말과 설정의 버전 표기도 맞춥니다. (`npm run release`가 앞의 네 파일이 모두 같은지 검사합니다)
> 과거 공지의 릴리스 번호와 숨김 키는 변경하지 않습니다.
> 5.6.0부터 시작 공지는 `src/lib/releaseNews.js`의 단일 공지를 사용합니다. 개발자의 말·5.1.2·5.5.0 공지는 자동으로 열지 않습니다. 과거 숨김 키는 보존하되 현재 공지 판정에 사용하지 않습니다.

### ② `src-tauri/.env` 준비 (빌드하는 컴퓨터에만)

```dotenv
NEIS_API_KEY=집에서_사용하던_나이스_인증키
POSTHOG_PROJECT_TOKEN=PostHog_설정에서_복사한_Project_token
POSTHOG_HOST=https://us.i.posthog.com
POSTHOG_DEV_ENABLED=0
```

- `NEIS_API_KEY`: 같은 키를 넣어 빌드하면 각 이용자의 앱이 포함된 키로 나이스 서버에 직접 요청합니다. 이용자가 인증키를 발급하거나 `.env`를 설치할 필요가 없습니다. 학교·캐시·메모는 이용자 PC에 저장합니다.
- 모든 설치본은 같은 키를 사용하므로 키 기준의 사용 한도도 공유합니다. 키를 변경하면 설치 파일을 다시 빌드해 배포해야 합니다.
- `POSTHOG_DEV_ENABLED=0`: 개발 앱은 전송을 끄고, release 설치본은 사용 통계를 자동으로 `environment=production`으로 전송합니다. 별도 테스트가 필요할 때만 테스트 프로젝트와 `POSTHOG_DEV_ENABLED=1`을 사용합니다.
- 시스템에 같은 이름의 환경변수가 있으면 `.env`보다 우선하므로 빌드 전 확인합니다. 키 없이 배포하는 `NEIS_ALLOW_NO_KEY=1` 우회 설정은 사용하지 않습니다.
- `.env`와 개인 키는 절대 릴리스에 첨부하거나 Git에 올리지 않습니다.

### ③ 설치 파일 만들기 — `npm run release`

```bash
npm run release
```

이 명령 하나가 다음을 순서대로 합니다. 하나라도 어긋나면 멈추고 이유를 알려 줍니다.

1. 버전 번호가 모든 파일에서 같은지 확인
2. **서명 키가 앱의 공개 키와 짝인지 빌드 전에 확인** (다른 키로 빌드하는 사고 방지)
3. 설치 파일 빌드 (Tauri가 설치 파일과 서명 `.sig`를 함께 만듭니다)
4. 만든 설치 파일의 서명을 앱과 같은 규칙으로 다시 확인
5. `output/release/v5.5.3/`에 **올릴 파일 두 개**를 준비
   - `Tidy.Task_5.5.3_x64-setup.exe` — GitHub가 공백을 점으로 바꾸므로 처음부터 그 이름으로 만듭니다
   - `latest.json` — 앱이 받을 파일 주소와 서명

> `npm run tauri build`를 직접 실행하면 서명 키가 없어 마지막에 실패합니다. 배포 빌드는 항상 `npm run release`를 쓰세요.
> 빌드는 성공했는데 준비 단계만 다시 하고 싶으면 `npm run release -- --skip-build`.

### ④ GitHub에 릴리스 발행하기

처음 한 번은 저장소의 **Settings → General → Releases → Enable release immutability**를
켜 둡니다. 이 설정은 앞으로 발행하는 릴리스의 태그와 설치 파일을 잠가, 실수로 이전
버전의 주소를 바꾸거나 파일을 삭제하는 일을 막아 줍니다. 설정을 켜기 전에 만든 릴리스에는
소급 적용되지 않습니다.

1. https://github.com/djqanrudgns12/Tidy-Task-Local/releases 로 이동
2. **Draft a new release** 클릭
3. **Choose a tag** → 아직 사용하지 않은 새 버전인 `v5.5.3` 입력 → *Create new tag* 선택
   - ⚠️ 태그는 반드시 `v` + `package.json`의 버전이어야 합니다. `latest.json`이 이 태그 아래의 파일을 가리킵니다
4. **Release title**: `Tidy Task 5.5.3` 처럼 입력
5. **Describe this release**: 달라진 점을 한 줄에 하나씩 적습니다
   ```
   - 테마를 15종으로 늘렸습니다
   - 메모가 가끔 저장되지 않던 문제를 고쳤습니다
   ```
   → 이 내용이 앱 안내 창의 "이번에 좋아진 점"에 그대로 표시됩니다
6. `output/release/v5.5.3/`의 **파일 두 개를 모두 첨부**합니다 (Attach binaries 영역에 끌어다 놓기)
   - ⚠️ `latest.json`을 빠뜨리면 앱 안 설치가 멈추고, 사용자에게 직접 내려받기를 안내합니다
   - ⚠️ 설치 파일을 빠뜨리면 앱은 릴리스 페이지 링크만 안내합니다
7. 먼저 **Save draft**를 눌러 제목·태그·첨부 파일을 다시 확인합니다
8. 이상이 없으면 **Publish release**를 누르고, **Latest** 표시가 새 버전에 붙었는지 확인합니다

> **이전 버전 보존 규칙:** 새 버전을 낼 때 기존 릴리스의 연필(Edit) 버튼으로 태그를
> 바꾸거나 기존 EXE를 삭제하지 않습니다. `Latest`는 최신 버전을 가리키는 표시일 뿐,
> 이전 릴리스를 지우는 기능이 아닙니다. 버전마다 서로 다른 릴리스와 EXE를 그대로 남겨야
> 구버전 앱에 저장된 다운로드 주소도 계속 작동합니다.

### ⑤ 사용자 앱과 같은 방법으로 확인하기 — `npm run release:verify`

```bash
npm run release:verify
```

Publish 직후 실행합니다. 사용자 앱과 똑같은 순서로 GitHub를 확인합니다.

1. 최신 릴리스 태그 → 앱이 안내할 버전
2. `latest.json` → 같은 버전인지, 윈도우 항목·서명·주소가 있는지
3. `latest.json`이 가리키는 설치 파일 → 이 릴리스의 첨부 파일인지, **실제로 내려받아 서명이 맞는지**

✅가 나오면 끝입니다. 실행 중인 사용자 앱은 최대 30분 안에, 앱을 다시 켜면 약 2초 뒤에 알림을 띄웁니다.

> 이 빠른 확인 로직은 5.1.2부터 적용됩니다. 아직 5.1.0 이하를 쓰는 사용자는 기존 확인 주기를 따르므로,
> 새 버전을 발행한 직후 바로 받으려면 **설정 → 앱 업데이트 → 업데이트 확인**을 누르면 됩니다.

## 4. 사용자(선생님)가 겪게 되는 화면

1. **얇은 알림 띠** — 작업을 가리지 않고 창 위쪽에 조용히 나타납니다
   - `×`를 눌러도 "영구 무시"가 아니라 **하루 미루기**입니다. 실수로 닫아도 내일 다시 알려 줍니다
   - 업데이트가 진행 중이면 같은 자리에 "새 버전을 내려받는 중 45%"가 보입니다
2. **안내 창** (띠를 누르면 열림)
   - 🔒 "지금까지 쓰신 할 일과 메모는 그대로 남습니다" — 가장 먼저 보이는 안심 문구
   - 이번에 좋아진 점 (릴리스 노트)
   - "이렇게 진행돼요" — 내려받기 → 잠시 닫힘 → 새 버전으로 다시 열림
   - **[지금 업데이트]** / [나중에] / [이 버전 건너뛰기]
   - 내려받는 동안: 진행률 막대와 **[취소]** (저장 단계부터는 취소할 수 없습니다)
   - 실패하면: 이유 + **[다시 시도]** + **[직접 내려받기]** + "Windows의 PC 보호" 대처법
3. **설치 직전** — 모든 메모 창에 "새 버전을 설치하고 있어요" 덮개가 잠깐 뜨고 입력이 잠깁니다.
   곧 앱이 닫히고, 설치 진행률 창이 뜬 뒤 새 버전이 저절로 열립니다
4. **설정 → 앱 업데이트** — 언제든 직접 확인하고 같은 [지금 업데이트]를 누를 수 있는 고정 경로

### 설치가 멈추는 경우와 안내

| 코드 | 언제 | 사용자에게 보이는 안내 |
|---|---|---|
| `NOT_PREPARED` | 릴리스에 `latest.json`이 없음 | 직접 내려받기로 설치해 주세요 |
| `VERSION_MISMATCH` | 태그와 `latest.json`의 버전이 다름 | 직접 내려받기로 설치해 주세요 |
| `CHECK_FAILED` / `DOWNLOAD_FAILED` | 인터넷 문제 | 연결을 확인한 뒤 다시 눌러 주세요 |
| `BAD_SIGNATURE` | 서명이 맞지 않음 (파일이 바뀌었거나 다른 키) | 설치하지 않았어요 |
| `EDITOR_BUSY` | 알림장·명단 창이 가져오기 중이거나 입력 중 | 그 창의 작업을 마친 뒤 다시 |
| `SAVE_FAILED` / `PREPARE_TIMEOUT` | 저장을 마치지 못한 창이 있음 | 내용은 그대로 있어요. 다시 눌러 주세요 |
| `LAUNCH_FAILED` | 보안 프로그램 등이 설치 프로그램 실행을 막음 | 직접 내려받기로 설치해 주세요 |

저장 확인 단계에서 멈추면 창의 입력 잠금은 곧바로 풀리고, 잠긴 동안 바뀐 내용도 다시 저장합니다.

## 5. 알아두실 점

- **저장소가 Public이어야 합니다.** Private으로 바꾸면 앱이 릴리스를 읽지 못합니다.
- **릴리스가 하나도 없으면** 앱은 조용히 넘어갑니다. 설정에서 직접 확인하면
  "아직 공개된 새 버전이 없습니다"라고 안내합니다. (오류가 아닙니다)
- **버전을 되돌리면(예: 5.5.3 → 5.5.1)** 앱은 업데이트로 인식하지 않습니다.
  버전 번호는 항상 올라가야 합니다.
- 사용자 데이터(`tidy-task-config.json`)는 `%APPDATA%\com.tidy.task` 아래에 저장되므로
  설치 파일을 덮어써도 **삭제되지 않습니다.** 업데이트 설치 모드에서는 설치 프로그램이 이 폴더를 건드리지 않습니다.
- 앱 안 설치 직전의 저장 파일은 `tidy-task-config.before-update.json`으로 남습니다(가장 최근 업데이트 한 번분).
  새 버전에서 문제가 생기면 앱을 끈 뒤 이 파일을 `tidy-task-config.json`으로 복사하면 설치 직전 상태로 돌아갑니다.
- 처음 설치(또는 직접 내려받기)에는 코드 서명 인증서가 없어 "Windows의 PC 보호" 경고가 뜹니다.
  앱 안 업데이트에서는 뜨지 않습니다.

## 급식창이 포함된 빌드

- 배포 빌드 전에 `src-tauri/.env` 또는 빌드 프로세스 환경변수에 `NEIS_API_KEY`를 설정합니다. 키가 없으면 release 빌드를 중단합니다.
- `.env`와 인증키를 Git에 올리지 마세요. 프런트엔드 `VITE_` 환경변수로 전달하지 않습니다.
- 인증키 난독화의 한계, 실제 API 검사 명령, 네이티브 검수 항목은 [급식창 구현과 검수](급식창-구현-검수.md)를 참고하세요.
