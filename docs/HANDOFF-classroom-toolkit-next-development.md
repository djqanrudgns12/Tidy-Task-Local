## 2. 확정된 제품 방향과 재개발에서 제외할 항목

### 이미 구현된 기반 — 회귀 검증 대상

- Tidy Task 본창과 별개인 독립 플로팅 툴바, 기본 항상 위.
- 버튼 영역을 포함한 드래그 이동, 클릭과 드래그 구분, 위치 저장.
- 가로/세로 선택, 아이콘과 ‘툴킷’ 글자를 클릭해 접기/펴기. 호버로 펼치지 않음.
- 최초 기본값은 툴킷 ON·펼침. 이후 사용자 설정을 로컬에 유지.
- 메인 설정과 모던 메뉴의 툴킷 ON/OFF, 툴킷 설정의 도구 노출 관리.
- 전광판·아날로그·모래시계·스톱워치의 독립 창. 타이머는 여러 번 열 수 있고 창별 종류는 고정.
- 타이머 창 크기 조절, 창별 항상 위 버튼과 기본 OFF, 시간 조작과 종류별 표현.
- 종류별 설정 공유·로컬 저장, 경고·종료·시계음 제어, 스톱워치 기록 타임라인.

이 항목들은 새 개발 목록에 다시 넣지 않는다. 다만 현재 도구 노출 관리와 창 생성 코드는 **타이머만 허용하는 부분이 있어**, 새 도구가 들어갈 때 해당 경계를 확장해야 한다.

### 유지할 사용자 결정

- 화면은 읽기 쉽고 직관적이며 귀엽고 아기자기하게. 과한 입체감·장식·다크톤으로 새 방향을 잡지 않는다. 현재 Tidy Task의 밝은 화면과 밀도를 따른다.
- 선택된 툴킷 아이콘은 **5번 하늘색 문구 케이스**. 확정 아이콘을 다시 후보 생성하거나 임의 교체하지 않는다. 투명 배경과 잘리지 않는 외곽을 유지한다.
- 제공된 샘플 이미지는 기능 참고용이다. 시각 디자인을 복제하지 않는다.
- 가능한 경우 기존 Bits UI 기반의 헤드리스 제어를 재사용한다. 라이브러리 도입 자체를 목표로 삼지 않는다.
- 타이머 설정은 종류별로 공유하지만 실행 상태·측정 기록은 영속 저장하지 않는다. 앱 종료 후 복원하지 않는다.
- BGM은 기각됐다. 타이머는 시계음·종료 경고음·종료음이며 해당 토글은 최초 ON, 로컬 저장. 종료음은 한 번 재생한다. 스톱워치에는 현재 없는 종료·경고 기능을 억지로 추가하지 않는다.
- 명단·알림장 내용·점수의 저장 정책은 타이머 기록 정책과 별도다. ‘모든 데이터가 종료하면 사라진다’고 확대 해석하지 않는다.
- 새로운 도구들도 별도 앱 창으로 사용한다는 방향이다. 각 도구의 다중 창 공유 방식은 별도 정의한다. 타이머의 독립 세션 방식을 명단 편집창에 그대로 복사하지 않는다.

## 4. 개발 순서와 단계별 완료 기준

난이도는 상대 평가다. 아래 ‘권장 초안’은 구현을 시작하기 위한 제안이며 사용자 확정 사항과 구분한다. 한 단계씩 완료하고 다음 단계로 넘어간다.

### 1단계. 학급 명단·모둠 등록 + 최소 확장 기반 — 중간

**확정 요구:** 툴킷 끝의 ‘학급 명단 등록’ 버튼, 학생 명단 등록, 모둠원 지정, 뽑기·점수판 등과 명단 공유.

**권장 초안:** 한 학급부터 시작하고, 이름 입력·여러 줄 붙여넣기·수정·삭제와 수동 모둠 배정을 제공한다. 다학급 전환·엑셀 가져오기·클라우드 동기화는 이번 단계의 필수가 아니다.

개발할 내용:

- 이름이나 배열 순서 대신 변하지 않는 학생 ID·모둠 ID를 사용한다. 동명이인을 같은 학생으로 합치지 않는다.
- 타이머 prefs와 별도의 버전 있는 로컬 저장 구조를 둔다. 명단·모둠·소속 참조의 유효성을 검사한다.
- 빈 이름, 중복 입력 안내, 미배정 학생, 모둠 삭제와 재배정의 규칙을 정한다.
- 명단 편집창은 하나를 재사용하는 방식을 우선 검토한다. 소비하는 도구 창들은 변경 알림 후 최신 데이터를 읽도록 한다.
- 여러 창의 동시 수정은 단일 저장 경로와 revision 등으로 통제한다. 오래된 화면이 전체 데이터를 덮어쓰지 않게 한다.
- 명단 버튼을 툴바 끝에 배치하고 가로/세로·접힘·화면 경계에서 잘리지 않게 한다.
- 6절의 타이머 전용 분기를 필요한 만큼 확장한다. 아직 만들지 않는 도구의 빈 화면·빈 저장 스키마는 넣지 않는다.

**완료 기준:** 등록 → 수정 → 모둠 배정 → 창 닫기/다시 열기 → 앱 재실행까지 데이터가 일관됨. 동명이인·빈 명단·삭제된 참조·저장 실패·구버전/손상 데이터 처리 검증. 타이머 설정과 사용자의 기존 메모·급식 데이터에 영향 없음.

**시작 시 결정할 정책:** 명단의 영속 저장은 권장안이며 세부 계약을 명시해야 한다. 학생의 복수 모둠 소속 허용 여부, 삭제 시 연결 데이터 처리도 함께 정한다. 학생 명단을 로그·분석 이벤트에 넣지 않는다.

### 2단계. 간단 뽑기 — 중간

**선행:** 1단계. **확정 요구:** 등록된 학급 명단을 가져와 그중에서 뽑는다.

- 권장 초안: 한 명 뽑기부터 완성하고, 당첨 중복 방지·대상 일시 제외·복수 인원 추첨의 필요성을 함께 정한다.
- 추첨 시점의 대상 목록을 고정하고 결과를 한 번 결정한 뒤 애니메이션으로 보여준다. 연출 중 명단 변경·연타가 결과를 바꾸지 않게 한다.
- 빈 대상, 전원 제외, 후보 소진, 명단 수정 후 대상 재구성, 창 닫기와 애니메이션 정리를 처리한다.
- 결과는 큰 이름과 명확한 상태로 보여준다. 중복 방지의 적용 단위와 초기화 시점을 정하고, 추첨 이력을 영속 저장한다고 임의 결정하지 않는다.

**완료 기준:** 명단 연동, 유효한 대상만 추첨, 결과와 연출 일치, 선택한 중복 정책 준수, 작은 창·키보드·반복 실행 검증. 음원 추가 시 출처와 이용 조건 기록.

### 3단계. 개인 점수판 — 중간

**선행:** 1단계. **확정 요구:** 점수판 메뉴의 ‘개인’ 유형.

- 학생 ID를 기준으로 표시와 점수를 연결한다. 권장 기본 조작은 점수 증감·직전 조작 취소·범위가 분명한 초기화다.
- 음수 허용, 증감 단위, 정렬, 여러 창의 점수 공유, 앱 종료 후 점수 보존 여부를 이 단계에서 정한다.
- 학생 개명·삭제·추가 시 점수 귀속을 유지하거나 정한 정책대로 처리한다. 자동 순위 재정렬 때문에 연속 클릭 대상이 바뀌지 않도록 한다.

**완료 기준:** 명단 변경 후에도 다른 학생에게 점수가 붙지 않음. 동시 조작 유실 없음. 실제 학급 규모에서 이름·점수·조작이 읽히고 초기화 범위가 명확함.

### 4단계. 모둠 점수판 — 중간~높음

**선행:** 1·3단계. **확정 요구:** 점수판 메뉴의 ‘모둠’ 유형과 등록 모둠 활용.

- 개인 점수판의 공통 조작·표시 구조를 재사용하되 점수 주체는 모둠 ID로 분리한다.
- 모둠 이름 변경·삭제·구성원 이동 시 점수 처리 규칙을 정한다.
- 개인 점수의 합계를 자동으로 모둠 점수로 쓰는 것은 확정 요구가 아니다. 우선 독립 모둠 점수를 권장한다.

**완료 기준:** 모둠 편집 후 점수가 섞이지 않음. 개인 점수와 저장·초기화 범위가 분명함. 여러 모둠을 한눈에 비교 가능.

### 5단계. 학급 온도계 — 낮음~중간

**확정 요구:** 점수판 메뉴의 ‘학급 온도계’ 유형.

- 권장 초안은 학급 전체의 공동 점수/진행도를 하나의 게이지로 표현하는 방식이다. 개인·모둠 점수 자동 합산은 미확정이다.
- 최소·최대·목표값, 증감 단위, 목표 도달 효과, 저장·초기화 정책을 정한다.
- 게이지와 실제 수치를 일치시키고 목표 도달 연출이 반복 발동하지 않게 한다.

**완료 기준:** 경계값·증감·초기화·목표 달성 표현이 일관됨. 색 외에도 숫자와 상태로 진행도를 알 수 있음.

점수판 조작을 재사용하려고 이 순서에 두었다. 독립 공동 점수 방식으로 확정되면 3단계 전으로 옮겨도 된다.

### 6단계. 알림장 — 기본형 기준 낮음~중간

**확정 요구:** 툴킷의 알림장 도구. 세부 작성·표시 방식은 아직 정하지 않았다.

- 권장 초안: 내용 작성과 교실용 큰 화면 표시, 글자 크기 조절, 로컬 초안 보존.
- 기존 Tidy Task 메모와 역할·저장 구조를 먼저 비교한다. 기존 메모를 알림장으로 간주하거나 기존 데이터를 임의 변환하지 않는다.
- 문서 저장·새 알림장·초기화의 의미를 정한다. 이미지 첨부·인쇄·템플릿·배포는 기본형 이후 별도 범위다.

**완료 기준:** 작성 → 표시 → 수정 흐름이 간결함. 긴 내용·한글 입력·작은 창을 처리하고 저장 실패가 조용한 데이터 유실로 이어지지 않음.

명단에 의존하지 않으므로 사용자 우선순위가 바뀌면 앞당길 수 있다.

### 7단계. 판서 — 높음, 화면 위 판서는 더 높음

**확정 요구:** 툴킷의 판서 도구. **미정:** 별도 창 안의 칠판인지, 다른 프로그램 위에 쓰는 투명 오버레이인지.

- 이 차이는 창·입력 구조에 직접 영향을 주므로 해당 단계 시작 시 묶어서 확인한다.
- 별도 창 방식의 권장 시작 범위는 펜·지우개·색·굵기·실행 취소/다시 실행·전체 지우기다.
- 창 리사이즈와 배율 변화에도 좌표를 유지하고, 펜·마우스·터치 입력 및 긴 획의 성능을 검증한다.
- 화면 위 방식이면 클릭 통과, 입력 모드 전환, 모니터별 좌표, 원래 프로그램 조작으로 복귀하는 동작까지 설계한다.

**완료 기준:** 실제 입력 기기에서 필기와 지우기가 안정적이며 창/배율 변화로 내용이 어긋나지 않음. 그림 저장·복원은 별도 정책에 따라 검증.

### 8단계. 롤린 썬더 연동 — 단순 실행은 낮음, 명단·결과 연동은 높음

**확정 요구:** 툴킷 기능으로 추가. 연동 깊이는 미정.

- 기존 `src/components/UpdateNotice.svelte`에 롤린 썬더 외부 링크 실행이 있다. 서비스 실행 로직을 새로 조사·복제하기 전에 재사용 가능성을 확인한다.
- 툴킷 실행 진입점은 아직 없으며, 기존 홍보 링크가 명단 연동을 구현한 것은 아니다.
- 단순 링크 열기와 별도 앱 창 요구가 어떻게 맞을지 확인한다. 원격 서비스를 권한 있는 로컬 WebView에 무작정 삽입하지 않는다.
- 명단 전달·게임 결과 수신은 실제 상대 서비스 인터페이스와 사용자 동의 범위를 확인한 뒤 별도 설계한다. URL 쿼리에 학생 명단을 직접 넣지 않는다.

**완료 기준:** 확정된 실행 방식과 오류/오프라인 처리가 동작함. 깊은 연동은 양쪽 앱의 데이터 계약과 검증까지 완료해야 완료로 본다.

### 작은 후속 항목: 스톱워치 기록 제목·메모

사용자가 나중의 고도화로 언급했다. 핵심 신규 도구보다 우선하지 않는다. 구현 시 lap ID로 제목·메모를 연결하고 현재 비영속 기록 정책을 유지한다. 기록 영속화는 별도 요구가 있어야 한다.

## 5. 새 도구마다 함께 완료할 공통 작업

- 실제로 동작하는 도구만 등록하고 노출 관리에 추가한다. 이름만 있는 실행 버튼은 만들지 않는다.
- 직접 실행과 하위 메뉴 실행을 구분하고, 툴바 끝의 명단 진입점을 유지한다.
- 도구 수 증가 시 가로/세로·접힘·노출 수 변경에 맞춰 창 크기와 화면 안 위치를 조정한다.
- 창 열기·재사용/새 창 생성·닫기·본창 종료·트레이 종료에서 수명과 저장 정책을 검증한다.
- 도구별 스타일을 분리한다. 기존 공통 `.tk-*` 변경으로 타이머나 툴바가 망가지지 않도록 한다.
- 표시 애니메이션과 실제 상태를 분리하고, 동작 줄이기 설정·키보드·포커스·이벤트/오디오 정리를 고려한다.
- 신규 저장소의 데이터·설정·일시 상태를 구분하고 마이그레이션과 손상 파일 보존을 설계한다.

## 6. 코드 지도와 실제 확장 시 주의점

경로는 저장소 루트 기준이다. 아래 파일을 전부 일괄 리팩터링하라는 뜻은 아니다.

| 경로 | 역할과 현재 제약 |
| --- | --- |
| `src/main.js` | 툴킷 독립 진입. 현재 toolkit/timer 라벨과 타이머 preview 종류만 인식. 새 창이 본 앱으로 잘못 진입하지 않게 확장 |
| `src/components/toolkit/ToolkitApp.svelte` | toolkit/settings/menu 이외를 모두 `TimerApp`으로 전달. 새 도구는 명시적으로 분기해야 함 |
| `src/lib/toolkit/registry.js` | 현재 `timer` 그룹만 등록. 도구 메타데이터 시작점이나 이것만 수정해서는 새 도구가 작동하지 않음 |
| `src/lib/toolkit/preferences.js` | `visibleToolIds` 정규화가 `timer`만 남김. 새 ID 허용과 구설정 호환을 함께 변경 |
| `src-tauri/src/toolkit.rs` | `visibleToolIds`는 최대 1개·timer만 허용. 역할 허용 목록, 창 라벨/크기/핀/작업표시줄, 작업창 판정도 타이머 중심 |
| `src-tauri/src/lib.rs` | 명령 등록과 창 종료 판정에서 `toolkit::is_work_window` 사용. 새 작업창이 열려 있는데 앱이 종료되지 않는지 확인 |
| `src/lib/toolkit/store.js` | 네이티브 invoke/event와 브라우저 preview 저장 경로. 현재 네이티브 설정은 `tidy-task-toolkit.json`, preview는 `tidy-toolkit-preview-v1` |
| `src/lib/toolkit/windows.js` | 창 실행과 타이머 메뉴 배치. `showTimerMenu`는 타이머 전용이고 메뉴 크기 244×250. 새 메뉴를 이 크기에 강제하지 않음 |
| `src/components/toolkit/ToolkitToolbar.svelte`, `ToolkitMenu.svelte`, `ToolkitSettings.svelte` | 툴바 렌더링·메뉴·노출 관리. 신규 ID, 직접 실행, 하위 메뉴를 끝까지 연결 |
| `src/lib/toolkit/drag.js`, `src/lib/windows/windowPlacement.js`, `windowRegistry.js` | 클릭/드래그 구분과 화면 위치 보정의 재사용 지점 |
| `src/lib/toolkit/toolkit.css`, `appearance.js` | 현행 디자인·테마 연결. 공통 수정의 영향 범위 확인 |
| `src-tauri/capabilities/default.json` | 현재 창 권한. 신규 native API 도입 시 필요한 권한 확인. 무관한 권한 확장을 하지 않음 |
| `src/lib/timers/`, `src/components/timers/` | 기존 타이머 로직·화면. 신규 명단·점수 저장과 분리 유지 |

현재 기술 구성: Svelte 5, Vite 8, Tauri 2, JavaScript + 일부 Svelte TypeScript, Bits UI 2.19.2. 일반 웹 UI만 추가하면 독립 네이티브 창까지 완성되는 구조가 아니다.

## 7. 검증과 남은 타이머 마무리

### 이미 기록된 결과와 현재 검증을 구분

- 2026-09-20 음원 QA에는 Node 테스트 170개 통과, 웹 빌드 통과가 기록되어 있다.
- 같은 문서에서 전체 `npm run check`는 기존 873 errors / 14 warnings로 실패했고, 해당 음원 수정 파일 진단은 0개였다고 기록했다.
- 이는 과거 실행 결과다. 이번 문서 작성에서 재실행한 결과가 아니며 이후 변경까지 통과했다고 간주하지 않는다.
- 최초 타이머 QA의 164개 테스트·공용 CC0 음원 설명보다 최신 음원 QA를 우선한다.

### 후속 구현의 검사

```powershell
npm.cmd test
npm.cmd run build
npm.cmd run check
cargo test --manifest-path src-tauri/Cargo.toml --lib toolkit::tests
```

- 위 명령은 저장소 루트에서 실행한다. 새 Rust 저장/창 모듈을 만들면 그 모듈의 테스트도 실행한다.
- 전체 check의 기존 실패와 이번 변경에서 생긴 진단을 구분한다. 무관한 저장소 전체 오류를 한꺼번에 고치지 않는다.
- 개발 웹 화면은 `npm.cmd run dev` 후 `/?toolkit-preview=toolkit` 및 `digital`, `analog`, `hourglass`, `stopwatch`로 확인할 수 있다. preview 분기는 개발 모드용이다.
- 브라우저 검증 후 실제 Tauri에서 창·항상 위·드래그·저장·다중 창 반영을 별도로 확인한다. 브라우저 성공을 네이티브 성공으로 보고하지 않는다.
- 사용자 실데이터 대신 별도 QA 데이터/환경을 사용하고, 검사 후 앱 설정과 자료를 임의 초기화하지 않는다.

### 문서상 남아 있는 실기기 검사

절전/복귀, 모니터 분리, 혼합 DPI와 100/125/150% 드래그, 네이티브 다중 창 장시간 메모리, 작업표시줄/트레이 종료 조합, 실제 교실 스피커 청감, 사용자 메모·급식 기능의 수동 회귀. 이후 다른 세션에서 완료됐을 수 있으므로 최신 기록을 먼저 확인한다.
